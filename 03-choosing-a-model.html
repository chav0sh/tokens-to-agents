Choosing a model

There are hundreds of models and the names change every few months. The decision underneath does not: three trade-offs, one hosting question, and a test on your own data.

The problem

The leaderboard does not know your task

Public rankings measure general ability on public test sets. Your app needs one narrow thing done well, within a budget and a response time. The top model on a leaderboard is often ten times the price and several times slower than a model that passes your cases just as well. And the model you pick today will be replaced: by a cheaper one, a better one, or because the provider retires it.

The picture

Filter, shortlist, test, watch

Hard limits (privacy, licence, where it may run) remove options first. Public benchmarks only build the shortlist. Your own evals make the decision.

Made-up prices in a realistic ratio. The gap is the point: about 8× for the same request.

Latency, worked

Two numbers describe speed. Time to first token is the wait before anything appears. Tokens per second is how fast the answer then arrives. For the same 150-token answer:

First tokenSpeedFull answer
Small model0.4 s100 tokens/s0.4 + 150 ÷ 100 = 1.9 s
Large model0.8 s40 tokens/s0.8 + 150 ÷ 40 = 4.55 s

Two levers follow. Streaming shows tokens as they arrive, so the user waits for the first token, not the last. And a shorter answer is a faster answer: the output length sets most of the time.

Use it when, skip it when

Where to start

Start with a small hosted model when

  • You are building the first version of anything.
  • The task is bounded and you give the model good context.
  • Volume is unknown or modest.

Leave that default only when

  • Evals still fail after the prompt and the context are fixed: move up a tier.
  • Law or policy says the data cannot leave: self-host.
  • Steady, very high volume makes GPUs cheaper than tokens: self-host.
  • It must run offline or on a device: a small open model.

Most quality problems are not model problems. A weak answer usually means the model was missing a fact or an instruction. Fix what you send before you pay for a bigger model.

In the docs assistant

One small model, behind one function

The assistant answers from passages it is given, which is a bounded task: a small, fast hosted model. The choice lives in exactly one place, so the model can be swapped without touching the rest of the app. It is the same idea as hiding a payment provider behind an interface.

import os
from langchain_core.language_models import BaseChatModel
from langchain_google_genai import ChatGoogleGenerativeAI
from langchain_nvidia_ai_endpoints import ChatNVIDIA

def get_llm() -> BaseChatModel:
    """The one place the chat model is created. Swap models here and nowhere else."""
    model = os.environ["LLM_MODEL"]   # the model name is configuration, not code
    if os.environ.get("LLM_PROVIDER") == "nvidia":
        return ChatNVIDIA(model=model, temperature=0, max_completion_tokens=512, timeout=60)
    return ChatGoogleGenerativeAI(model=model, temperature=0, timeout=60)

Because every chat model has the same invoke, the rest of the code does not know which company answers. When a model is retired, or a cheaper one appears, you change one environment variable, rerun the evals, and compare the scores.

Pin the exact model version where the provider lets you, and treat a model change like a dependency upgrade: run the evals before it reaches users.

Try it. Take your provider's price page and work out what 10,000 requests a day would cost on its smallest and its largest model, using the sum from chapter 1.
