Extras · A second app

Case study: the voting assistant

Consider a second, larger app built from the same patterns. It reads a shareholder voting policy and a company's annual meeting agenda, and recommends a vote on each item, naming the policy rule it applied. This page takes it apart: what it is for, what it is made of, and how one vote travels through it.

How it helps someone vote

An investor who owns shares in many companies has a vote at each one's annual general meeting (AGM). Every agenda has ten to twenty items: electing directors, approving the dividend, pay programmes, shareholder proposals. Most investors have a written voting policy that says how to vote in each situation. Applying it means reading every item of every agenda against every rule, in the few weeks when all the meetings happen at once.

What you give it

A policy and an agenda

The policy: numbered rules such as "vote AGAINST directors who sit on more than 4 public boards". The agenda: the items of one meeting, each a title and a short text.

What you get back

A vote, a rule, a reason

For every item: FOR, AGAINST or ABSTAIN, the ID of the one rule that decided it, and one sentence naming the fact that mattered.

What stays with you

The decision

It recommends; a person reviews and votes. Because every recommendation cites its rule, checking one takes seconds instead of a re-read of the policy.

What it is good for

  • Speed: a whole agenda in the time it takes to read one item.
  • Consistency: the same rule is applied the same way at every company.
  • Traceability: each vote points at a rule, so "why did we vote against?" always has an answer.
  • Catching what is not in the text: a director's other board seats come from a database, not from the agenda.

What it does not do

  • It does not vote. A person decides.
  • It knows only its policy. A situation no rule covers gets the nearest rule, which may be wrong.
  • It trusts the agenda's facts and the board data it was given.
  • It is a small learning project on made-up data: 11 rules, 3 sample agendas, 4 directors. Not advice.

One vote, through the system

Item 7 is the instructive one. The agenda says Anna Berg is independent and attended 11 of 12 meetings. On the text alone she should be elected. Here is what happens instead.

  1. Retrieve the rules Qdrant + BM25

    DoesSearches the 11 policy rules with the item's title and text, by meaning and by exact words, and keeps the best three.

    GivesThe rules about electing directors, with their IDs.

  2. Look up graph facts Neo4j

    DoesSees that the title is "Elect … as director", takes the name, and asks the graph how many companies she sits on the board of.

    GivesOne line: "Anna Berg sits on 5 public boards."

  3. Recommend the model

    DoesReads the three rules, the item and the fact, each in its own tagged block, and follows a numbered procedure: find the one rule that decides, apply it exactly.

    GivesA reason, then rule 3.2, then the vote: AGAINST.

  4. Check the citation plain code

    DoesConfirms that the rule the model cited is one of the three it was shown. If not, the model is asked once more, with the allowed IDs listed.

    GivesA recommendation whose rule was checked against the three shown. If the second try also fails, the answer is kept but the run log marks it as not verified.

No search could have found this. "5 public boards" is written nowhere. It is a count of connections between a person and companies, so it lives in a graph, and a query produces it. That is the whole of chapter 11 in one agenda item.

Does every input use everything?

Almost. This app is a fixed pipeline: every item goes through the same four steps in the same order, and no model decides what to run. Two things do depend on the input.

Depends on the input

The graph is asked only about directors

The code looks at the title. "Elect … as director" triggers the Neo4j query; any other item gets the fact "None." and Neo4j is not touched.

Example. Erik Lund is looked up too (2 boards), but his vote is decided by the word "PEP" in the agenda, which keyword search matched to rule 3.4.

Depends on the model's answer

The retry runs only after a bad citation

If the cited rule is not one of the three shown, the model is asked once more with the allowed IDs. At most two attempts, then the flow stops.

In practice. On the ten test items the first answer passed every time: zero retries recorded.

What changes most from item to item is not which parts run but what they return: a different three rules from the search, a different fact from the graph, and so a different prompt.

Three ways an app can decide what runs

Fixed pipeline

The voting assistant

Every input is the same kind of thing, an agenda item, so every input takes the same path. Predictable cost, and nothing can be skipped.

Routed workflow

This book's docs assistant

Inputs are free questions, so a router sorts them first. A policy question uses the handbook search; a holiday question adds the HR lookup; anything else is refused after one model call, with no search at all.

Agent

A coding or helpdesk assistant

The model picks each next step from its tools. Two requests can use completely different parts, in a different order, a different number of times.

The three shapes are compared in chapter 13. Choose the simplest one your inputs allow.

The system, in short

The voting assistant a fixed workflow: every item takes the same path

  1. Agenda item
  2. Retrieve rulesQdrant + BM25, fused
  3. Graph factsboard seats, from Neo4j
  4. Recommendreason, rule, vote
  5. Check the citationretry once if wrong
  6. Vote, rule, reason
Interface
A web app behind a sign-in. Pick an agenda, press run, get a table of votes; click a row to see why. A history of earlier runs per agenda.
Tools
None that the model chooses. The search and the graph lookup are called by code for every item, so they cannot be skipped.
Database
Policy rules in Qdrant, board seats in Neo4j, every model call in a small SQLite run log.
Qdrant or Neo4j?
Qdrant + Neo4j The text gives the rule; the graph gives the fact the rule needs.

In the terms of Compare and combine, it is system 8, the knowledge assistant that needs both stores, built as a pipeline rather than a chat.

Every part, and what it does here

Finding the rules

Data

The policy file

A markdown file of 11 numbered rules. Each rule is one chunk and carries its ID, so whatever the search returns can be cited.

Chapter 9 →
Embedding model

fastembed

Turns each rule, and each agenda item, into 384 numbers on the local CPU. No API key, and the policy never leaves the machine.

Chapter 5 →
Vector database

Qdrant

Holds the 11 rule vectors and returns the three nearest in meaning. Only policy rules are indexed: agenda text is searched with, never stored.

Chapter 6 →
Keyword index

rank-bm25

Finds rules that share the item's rare words. It is what catches "PEP" in item 5, which the vector search missed.

Chapter 7 →
Fusion

Reciprocal rank fusion

Merges the top three by meaning with the top three by words and keeps the best three overall. No reranker: with 11 rules, three candidates are enough.

Chapter 8 →

Finding the facts

Graph database

Neo4j

Stores directors, companies, and a SITS_ON link between them. One Cypher query counts a nominee's boards. The name goes in as a parameter, never into the query text.

Chapter 10 →
Pattern

A resolved fact, not raw data

The prompt gets "sits on 5 public boards", not a list of five companies to count. The database counts; the model reads.

Chapter 11 →

Deciding, and checking

Model

A small hosted model, through LangChain

One function creates the chat model, and a setting picks the provider (Google or NVIDIA). The rest of the code does not know which one answers.

Chapter 3 →
Structured output

Reason, rule, vote

The answer must fit a schema: a short reason, one rule ID, and exactly FOR, AGAINST or ABSTAIN. The reason comes first, so the vote is written after the thinking.

Chapter 2 →
Flow

LangGraph

Four nodes in a line (retrieve, graph facts, recommend, check) and one edge that loops back for a retry, with a hard limit of two attempts.

Chapter 15 →
Guard

The citation check

Plain code after the model: the cited rule must be one of the three it was shown. The model's output is treated as untrusted.

Chapter 18 →
Prompt

Versioned prompt files

The prompt is a file with a version number, never edited once evaluated. Version 2 puts rules, item and facts in tagged blocks, so agenda text cannot pose as an instruction.

Chapter 18 →

Knowing it works

Evals

Ten cases, two scores

The ten sample items with their expected vote and rule. One command runs them and prints vote accuracy and rule accuracy.

Chapter 17 →
Monitoring

A run log in SQLite

Every model call is recorded: tokens including thinking, duration, model, prompt version, errors. A page charts them per run.

Chapter 19 →
Interface

Streamlit

A Python library that turns scripts into web pages. It gives the app its sign-in, the recommendations table, the run charts and the prompt switch.

How it got to ten out of ten

One build of this design went in steps, each aimed at a case the step before got wrong. These are the scores it reached on the ten items.

  1. A stub that always votes FOR 3/10

    AddedNothing: the floor. Anything that scores no better has learned nothing.

    ShowsThree of the ten items happen to be FOR.

  2. RAG with vector search 8/10

    AddedEmbeddings, Qdrant, a prompt.

    Still failsItem 5: the rule with the exact term "PEP" is not retrieved. Item 7: the board count is in no text.

  3. Keyword search and rank fusion 9/10

    AddedBM25 next to the vector search.

    FixesItem 5. Item 7 still fails.

  4. A LangGraph flow with a citation check 9/10

    AddedThe flow and the guard.

    FixesNothing here: the check passed first time on all ten. It is insurance, not an improvement.

  5. Board seats from Neo4j 10/10

    AddedThe graph, and one fact line in the prompt.

    FixesItem 7: five boards, AGAINST. Item 8, with exactly four, stays FOR.

  6. A second prompt version 10/10

    AddedA system message and tagged data blocks.

    ShowsBoth versions scored 10/10 in three runs out of three. The new one was adopted for its defence against injected text, at a cost in tokens.

  7. A different model provider 9/10, then 10/10

    ChangedThe model, by one setting.

    ShowsOne item was voted wrongly while the model's own written reason was right, because the vote field came before the reason field. Reason first fixed it.

What the second app confirms

Vector search misses exact terms; keyword search finds them.One item fixed by the keyword "PEP".
Some facts are in relationships, and no text search will find them.A count of board seats, from the graph.
Let the database answer the exact question and hand the model a finished fact."Sits on 5 boards", not a list to count.
Reason first, then the verdict.Same model, same facts, a wrong vote until the field order changed.
