LangGraph

LangGraph is a library for writing a flow as a graph: steps are nodes, the paths between them are edges, and one shared state travels through. It is a state machine with the plumbing an AI app needs: saved progress, loops, pauses for a person, and a picture of where a run went.

The problem

If/else works, until the flow has to wait or retry

Chapter 13's workflow was a plain function, and for a straight path that is the right tool. It starts to hurt when the flow needs any of these:

NeedIn a plain function
Retry one step when a check fails, at most three times.Nested loops and counters around your logic.
Stop before a risky step and wait for a person to approve it, perhaps for a day.The function cannot pause. You save everything by hand and write code to pick it up again.
Continue a conversation tomorrow.You build your own storage for what was said and decided.
See which path a run took, and resume one that crashed halfway.Logging you add yourself, and no resume.

How it works

State, nodes, edges

PieceWhat it isLike
StateOne typed dictionary for the whole run: the question, what was found, the answer. Every node can read all of it.The request context passed down a middleware chain.
NodeA function. It receives the state and returns only the keys it wants to change.One middleware, or a reducer.
Edge"After this node, run that one."A transition in a state machine.
Conditional edgeA function that looks at the state and returns the name of the next node.A router.
CheckpointerSaves the state after every node, under a conversation ID.A session store, written after each step.

A node returns only what changed

class State(TypedDict, total=False):
    question: str
    kind: str              # policy, my_holiday or other
    employee: str
    days_requested: int
    passages: str
    answer: str
    history: list[str]     # earlier questions and answers of this conversation

def retrieve_node(state: State) -> State:
    return {"passages": search_handbook.invoke({"question": state["question"]})}   # one key; the rest is kept

def after_retrieve(state: State) -> str:
    return "holiday" if state["kind"] == "my_holiday" else "answer"               # the name of the next node

LangGraph merges each node's return value into the state and then follows the edges. Your functions never call each other, which is what lets the library stop between them, save, and resume.

What the checkpointer buys you

FeatureHow it follows from saved state
ConversationsCall the graph again with the same ID and it starts from the saved state: the history is there. Chapter 16 uses this.
Human in the loopA node can interrupt the run. The state waits in storage until someone approves, minutes or days later, then the run continues from that node.
Resume after a crashRestart from the last saved node instead of repeating model calls you already paid for.
InspectionThe saved states are a step-by-step record of the run.

Loops are just edges that point backwards

The evaluator loop from chapter 13 is one conditional edge: after a check node, go back to answer if the check failed and fewer than three attempts were made, otherwise go to END. The attempt counter lives in the state. An agent is the same shape: a model node and a tools node with an edge in each direction.

Use it when, skip it when

When a graph earns its place

Use LangGraph when

  • The flow has branches and loops you want to see and test as separate steps.
  • Runs must pause for a person, or continue across requests.
  • You need conversations with saved state and do not want to build that storage.

Skip it when

  • The flow is a straight line of two or three calls. A function is clearer.
  • It is a batch job with no conversation and no pauses.
  • You already run a workflow engine (Temporal, a job queue with retries) that gives you durability. Use that for the long-running part.

In the docs assistant

The workflow becomes a graph

from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import END, START, StateGraph

graph = StateGraph(State)
graph.add_node("route", route_node)
graph.add_node("retrieve", retrieve_node)
graph.add_node("holiday", holiday_node)
graph.add_node("answer", answer_node)
graph.add_node("refuse", refuse_node)

graph.add_edge(START, "route")
graph.add_conditional_edges("route", after_route, ["retrieve", "refuse"])       # decided at run time
graph.add_conditional_edges("retrieve", after_retrieve, ["holiday", "answer"])
graph.add_edge("holiday", "answer")
graph.add_edge("answer", END)
graph.add_edge("refuse", END)

app = graph.compile(checkpointer=InMemorySaver())      # save the state after every node

result = app.invoke(
    {"question": "I'm Maria Lind. I want to take 10 days off next month. Do I have enough holiday left?"},
    {"configurable": {"thread_id": "maria-1"}},        # the conversation this run belongs to
)
print(result["answer"])
You have 7 holiday days left, which is not enough for 10 days. [Holiday policy]

The node functions are the same code as in chapter 13, cut at the step boundaries. What changed is that the wiring is now data: it can be drawn, and each node can be tested by handing it a state.

Try it. In app/agent.py, add a check node after answer that verifies the answer names a document, and an edge back to answer when it does not, with an attempt limit. That is the evaluator loop.
