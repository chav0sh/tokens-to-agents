Monitoring, cost, caching

Running an AI app is running a service that depends on a slow, metered, changing API. Most of this chapter is operations you already know: logs, traces, timeouts, retries, caches. What is new is what you measure, and three kinds of cache.

Prompts and answers are user data. Logging the full text is what makes debugging possible, and it is also personal data in your logs. Decide who can read it, how long it is kept, and whether to mask it. Never log API keys.

Three caches

CacheKeyHit whenRisk
ExactThe normalised question (or the whole prompt).The same question again.Stale answers after the documents change. Clear it when you re-index.
SemanticThe question's embedding.A question that is similar enough to a cached one.Serving the answer to a different question.
Prompt caching (by the provider)The unchanged beginning of your prompt.The next call starts with the same long prefix.None for correctness. It only reduces price and latency for the repeated part.

The exact cache, measured on the docs assistant:

CallTime
"What do I do if my computer is stolen?" (first time)849 msa miss: full pipeline
The same question againunder 0.1 msa hit
"what do I do if my computer is STOLEN? "under 0.1 msa hit: the key is lower-cased and trimmed
"My laptop was stolen, what now?"708 msa miss: same meaning, different words

The last row is what a semantic cache is for. Before reaching for one, remember chapter 5: to the embedding model, "When do I need FIN-140?" and the FIN-401 chunk scored 0.72, higher than the right one. A semantic cache with a loose threshold would hand one form's answer to a question about another, with no model involved to notice. If you use one, set the threshold with an eval and keep it tight.

Prompt caching rewards one habit: put what never changes (instructions, tool descriptions, examples) at the start of the prompt and what changes (passages, the question) at the end. Providers charge less for a repeated prefix and process it faster.

When the provider fails

PracticeDetail
TimeoutsOn every call. A hung request must fail, not hold a worker.
Retries with backoffFor rate limits and server errors. Not for a 400: the request is wrong and will stay wrong.
A fallbackA second model or provider, behind the single function from chapter 3. Run your evals on it before you need it.
Validate, then repair or refuseOutput that fails its schema gets one retry with the error included, then a clear failure.
Pin versionsOf the model where you can, and of your libraries always.

A gateway is one service in front of all your model calls that does these things in one place: keys, rate limits, fallbacks, logging, spending caps. It becomes worth having when several apps or teams call models.

Use it when, skip it when

What to build first

From day one

  • A log line per model call: tokens, duration, model, prompt version, error.
  • A timeout and a retry limit on every call.
  • A cap on output tokens, and a spending alert at the provider.

When the numbers ask for it

  • An exact cache: when logs show the same questions repeating.
  • A tracing tool: when a request has more steps than you can follow in a log.
  • A semantic cache, a gateway, a fallback provider: when volume, cost or downtime justify another moving part.

In the docs assistant

A stopwatch and a dictionary

started = time.perf_counter()
vector = vector_search(question);    after_vector = time.perf_counter()
keyword = keyword_search(question);  after_keyword = time.perf_counter()
ranked = rerank(question, fuse(vector, keyword)); after_rerank = time.perf_counter()
reply = ask(question, passages);     finished = time.perf_counter()

print(reply.usage_metadata)      # {'input_tokens': 145, 'output_tokens': 18, 'total_tokens': 163}
CACHE: dict[str, str] = {}

def cached_answer(question: str) -> str:
    key = " ".join(question.lower().split())          # exact match after trimming and lower-casing
    if key not in CACHE:
        CACHE[key] = ask(question, passages_for(question)).content
    return CACHE[key]

Crude and sufficient for a first version. In a real service the cache needs an expiry, has to be cleared when the handbook is re-indexed, and must include the user in the key whenever answers depend on who is asking.
