Part 5 · Designing the system · Chapter 22

Problem → pattern → tool

A method for designing an AI system from a blank page. Start from the problem, pick the patterns it needs, and only then choose tools. Seven questions, a few lookups, and one page you can fill in for your own project.

The problem

Most designs start from the wrong end

"We should use agents." "Let's put it in a vector database." "Which framework?" These are tool decisions made before anyone has written down what a good output looks like. The result is a system shaped by its tools: retrieval where a lookup was needed, an agent where three fixed steps would do.

The patterns in this book are few. Almost every AI product is some combination of a handful of them. Design is choosing which, in what order, for which part of the problem.

The picture

Three decisions, in this order

  1. The problemthe task, a good output, what a mistake costs
  2. The patternswhere facts come from, who decides the steps, what checks it
  3. The toolswhatever fills each slot with the least new machinery
  4. The numbersan eval set, a latency budget, a cost per request

Try it on your own idea

How it works

Seven questions before any code

  1. What is the task, and what does a good output look like?

    DoWrite ten real inputs, each with the output you would accept.

    It decidesEverything. Those ten cases are your first eval set. If you cannot write them, the project is not ready to build.

  2. Where do the facts come from?

    OptionsThe model's own knowledge, your documents, a live system, relationships between things.

    It decidesNothing extra, retrieval, tools, or a graph.

  3. What comes out, and who consumes it?

    OptionsText for a person, data for a program, an action in another system.

    It decidesAnswers with sources, structured output with a schema, or an action behind a confirmation.

  4. Are the steps known in advance?

    OptionsAlways the same, a few branches, or unknown until you look.

    It decidesOne call, a workflow, or an agent.

  5. What does a mistake cost, and who catches it?

    OptionsA shrug, an annoyed user, or money and legal trouble.

    It decidesHow much evaluation and guarding, and whether a person approves.

  6. How fast and how cheap must it be?

    DoAdd up the model calls, their tokens and their seconds before building.

    It decidesThe model tier, the number of calls, streaming, caching.

  7. What changes, and how often?

    Think ofDocuments, prompts, models, the questions people ask.

    It decidesIndexing jobs, versioning, monitoring, and how you find out it got worse.

Budgets, worked for the docs assistant

StepTimeTokens in / out
Route the question (model call)about 1 s300 / 20
Retrieve, fuse, rerankabout 0.05 snone
Write the answer (model call)about 1 s1,500 / 150
Per questionabout 2 s1,800 / 170

At example prices of $0.30 and $2.50 per million tokens that is $0.000965 per question, or about $48 for 50,000 questions a month. Two things follow at a glance: the two model calls are the whole response time, so making retrieval faster is pointless; and the bill is small enough that developer time, not tokens, is what to optimise. Do this sum before you build. It takes five minutes and often changes the design.

Times are rounded from this book's measurements; token counts for a realistic prompt are estimates (the demo app's measured call in chapter 19 was much smaller, 145 tokens in and 18 out, because its handbook chunks are short); prices are examples.

Use it when, skip it when

Should this be an AI feature at all?

A good fit

  • The input or output is language, and rules would never cover the variety.
  • A person checks the result, or a wrong result is cheap and visible.
  • You can write down ten cases and what a good output is for each.
  • "Mostly right, much faster" is a real improvement on today.

A poor fit

  • The task has an exact answer that a query or a rule computes.
  • Every output must be right and nothing checks it.
  • Nobody can say what a good output looks like.
  • The honest reason is "we need something with AI in it".

The tools

From pattern to tool

  1. Model

    Start withA small hosted model.

    Move whenEvals fail after prompt and context are fixed: a larger tier. Privacy or very high volume: self-hosting.

  2. Vector search

    Start withThe database you already run (pgvector), or vectors in memory.

    Move whenScale, filtering or hybrid queries call for a dedicated vector database.

  3. Keyword search

    Start withYour database's full-text search, or a small library.

    Move whenSearch quality matters: Elasticsearch or OpenSearch.

  4. Graph

    Start withA table and a recursive query.

    Move whenPaths are deep, varied or central: a graph database.

  5. Flow

    Start withA plain function.

    Move whenYou need loops, pauses or saved conversations: LangGraph.

  6. Evals and logs

    Start withA script and a table.

    Move whenSeveral people need to compare runs: a platform.

  7. Glue

    Start withThe provider's SDK, or LangChain's interfaces.

    Move whenMore of a framework removes real work, and only there.

The left column is always "what you already have". New infrastructure has to earn its place with a failing eval or a missed budget.

In the docs assistant

The one-page design

The seven questions, answered for the app in this book. This page is the design document: if you can fill it in for your project, you are ready to build.

QuestionThe docs assistant
1. Task and good outputAnswer an employee's question about company policy in one or two sentences, naming the document. Twelve test questions, plus two it must decline.
2. FactsThe handbook (retrieval), the HR system (a lookup), the org chart (a graph query).
3. OutputText for a person, with its source.
4. StepsKnown, three branches: policy, own holiday, other. A workflow with a router.
5. Cost of a mistakeAn employee acts on a wrong rule. Medium. So: "I don't know" allowed, sources shown, output checks, a faithfulness eval.
6. Speed and priceAbout 2 seconds and a tenth of a cent per question. A small model; no cache needed yet.
7. What changesThe handbook (re-index on change), the model (pinned, evals before switching), the prompt (versioned).
