Memory and MCP

Two loose ends of building a flow. Memory: how an app built on a stateless model remembers a conversation. MCP: a standard plug for tools, so the same tool can serve many AI apps. Both are words you will hear in every project.

The problem

The model forgets, and every app rebuilds the same tools

Memory. Maria asks whether she can take 10 days off, gets "no", and follows up: "And would it be enough for 5 days instead?" On its own that sentence means nothing: enough of what, for whom? The model keeps no state between calls (chapter 1). If the app does not carry the conversation, nobody does.

Tools. Chapter 12's holiday lookup is a Python function inside one app. The chat assistant, the coding assistant and the support bot each want the same lookup, and each would write it again in its own format. Tools need a socket that fits them all.

MCP: tools behind a standard protocol

  1. Your AI appthe "host": a chat app, an IDE, your own agent
  2. MCP clientinside the app; speaks the protocol
  3. MCP servera separate program offering tools, data and prompts
  4. The real systemHR database, GitHub, files, a search engine

The Model Context Protocol (MCP) is an open standard, introduced by Anthropic in late 2024 and since adopted widely. The client asks the server "which tools do you offer?", gets names, descriptions and argument schemas, and can then call them. It does for AI tools what the Language Server Protocol did for editors: write the server once, use it from every client.

How it works

Memory is state you send again

The same follow-up, with and without memory

The graph from chapter 15 saves its state per conversation ID. Two real runs of the follow-up "And would it be enough for 5 days instead?":

Same conversation as Maria's first question

"Yes, you have enough holiday days left for 5 days. You have 7 days remaining, which is more than the 5 days you are requesting."

The saved history told the router who is asking and what "it" refers to.

A new conversation

"Yes, full-time employees receive 25 days of paid holiday per year, and up to 5 unused days can carry over to the next year."

Fluent, confident, and not an answer to the question. It does not know who is asking.

"Memory" here is nothing more than this: the earlier questions and answers are stored, and put back into the prompt on the next turn.

History grows; the window and the bill do not forgive

Every turn resends everything before it, so the cost of a conversation grows with the square of its length. Three standard ways to keep it in check:

StrategyHowLoses
WindowKeep only the last N turns.Anything said earlier, completely.
SummaryA model call condenses older turns into a paragraph that stays in the prompt.Detail, and it costs an extra call.
RetrieveStore all turns; search for the ones relevant to the new message.Whatever the search misses. This is RAG over the conversation.

Most apps start with a window and add a summary when conversations get long.

Memory is personal data. What users tell an assistant gets stored. Decide what is kept, for how long, and how a user can see and delete it. And never let one user's memory be searched for another user's question: filter by user in the query, as in chapter 6.

MCP: a server and a client, for real

The holiday lookup as an MCP server is the same function with a different decorator:

from mcp.server.mcpserver import MCPServer

server = MCPServer("hr-tools")

@server.tool()
def holiday_days_left(employee: str) -> str:
    """How many paid holiday days an employee has left this year. Needs the employee's full name."""
    if employee not in HOLIDAY_DAYS_LEFT:
        return f"No employee called {employee!r}."   # a readable error (chapter 12), never a made-up 0
    return f"{employee} has {HOLIDAY_DAYS_LEFT[employee]} holiday days left this year."

if __name__ == "__main__":
    server.run()      # stdio: the client starts this file as a subprocess and talks over stdin/stdout

Any MCP client can now discover and call it, without knowing it is Python or what it talks to:

from mcp import Client
from mcp.client.stdio import StdioServerParameters

async with Client(StdioServerParameters(command=sys.executable, args=["mcp_server.py"])) as client:
    for tool in (await client.list_tools()).tools:
        print("tool:", tool.name, "-", tool.description)
    result = await client.call_tool("holiday_days_left", {"employee": "Maria Lind"})
    print("result:", result.content[0].text)
tool: holiday_days_left - How many paid holiday days an employee has left this year. Needs the employee's full name. result: Maria Lind has 7 holiday days left this year.
An MCP server can offerWhat it is
ToolsFunctions the model may ask to call. By far the most used part.
ResourcesData the app can read and put into the prompt: files, records.
PromptsReusable prompt templates the user can pick.

Servers run either as a local subprocess (stdio, as above) or as a remote service over HTTP.

An MCP server is code you trust. Its tool descriptions go straight into your model's prompt and its tools act with whatever access you give them. Installing an unknown server is like installing an unknown package that can also talk your model into things. Use servers from sources you trust, and give each the narrowest permissions that work.

Use it when, skip it when

How much of each do you need?

Add it when

  • Conversation history: the product is a chat. Follow-up questions are the whole point.
  • Long-term memory: users come back and expect the app to know them.
  • MCP: a tool should be usable from several apps, or you want to plug existing servers (GitHub, a database, a browser) into your agent or your coding assistant.

Skip it when

  • Any memory: the app is one-shot: classify this, extract that, answer a single search. Stateless is simpler, cheaper and easier to test.
  • Long-term memory: you have no clear idea what is worth remembering. A wrong memory is worse than none.
  • MCP: the tool is used by one app. A plain function (chapter 12) is less to run.

In the docs assistant

A conversation ID is all it takes

def answer_node(state: State) -> State:
    earlier = "\n".join(state.get("history", []))
    passages = state["passages"] + (f"\n[Earlier in this conversation]\n{earlier}" if earlier else "")
    answer = write_answer(state["question"], passages)
    # The history is part of the state, so the checkpointer saves it with everything else.
    return {"answer": answer, "history": [*state.get("history", []), f"Q: {state['question']}", f"A: {answer}"]}

conversation = {"configurable": {"thread_id": "maria-1"}}
app.invoke({"question": "I'm Maria Lind. I want to take 10 days off next month. Do I have enough holiday left?"}, conversation)
app.invoke({"question": "And would it be enough for 5 days instead?"}, conversation)     # same ID: it remembers

The router also receives the history, which is how it knew the follow-up was about Maria's holiday. With InMemorySaver the memory lasts as long as the process; a SQLite or Postgres saver makes it survive a restart.

Try it. uv run python app/mcp_client.py starts the MCP server and calls its tool. If you use an assistant or an IDE that supports MCP, point it at app/mcp_server.py and ask it how many holiday days Tom Ek has left.
