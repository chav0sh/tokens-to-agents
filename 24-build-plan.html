Your build plan

The last chapter is about the first day. What to build, in what order, with which tools, and how to use an AI coding assistant to get there quickly without losing track of what you built.

The problem

Knowing the parts is not the same as starting

You can now name every box in an AI architecture. The usual next mistake is to set them all up before writing a line that answers a question: a vector database, a framework, a tracing platform, an agent. Three weeks later there is infrastructure and no product. The way through is the opposite: something working and measured on day one, and one improvement at a time after that.

The picture

The order of work

  1. 1. Ten casesreal inputs, the output you would accept
  2. 2. One calla prompt, a model, a score
  3. 3. Add the factsretrieval or a lookup; score again
  4. 4. Fix the worst failureone change, rerun, keep or undo
  5. 5. Checks and a logvalidate, limit, record
  6. 6. Three real userstheir questions become new cases

Step 1 comes before any prompt: evaluation-driven development (chapter 17). Steps 4 and 6 repeat for as long as the product lives. Everything in Parts 2 to 4 of this book is something you might do at step 4, when a failure calls for it.

How it works

A first project, in a weekend

  1. First hour the cases

    DoPick a small problem you actually have. Write ten inputs and, for each, what a good output is. Get one API key.

    You haveAn eval set. The hardest and most valuable hour.

  2. Second hour the baseline

    DoOne file: a prompt, one model call, a loop over the ten cases, a printed score. Temperature 0, a cap on output tokens, a timeout.

    You haveA baseline number, however bad.

  3. Rest of day one the prompt

    DoRead the failures. Add rules, a way out, the output format. If facts are missing, paste them in by hand to prove that facts are the problem.

    You haveKnowledge of whether this is a prompt problem or a facts problem.

  4. Day two, morning the facts

    DoSplit your documents, embed them, search, put the top chunks in the prompt. Or call the system that has the value. Print what was retrieved for every failure.

    You haveA working RAG or tool-using app, with a score that moved.

  5. Day two, afternoon the safety net

    DoValidate the output in code. Log tokens and time per call. Add two cases that must be declined. Show it to someone.

    You haveSomething you can leave running and learn from.

That is chapters 1, 2, 4, 5 and 17 of this book, and about a hundred lines of code. Vector databases, rerankers, graphs, flows and agents come later, each when a failing case asks for it.

Building it with an AI coding assistant

Most code today is written with an AI assistant, and AI apps are no exception. It makes starting fast. It also makes it easy to end up with a system you cannot explain. Some habits that keep the speed and the understanding:

Give it your ten cases first

Ask for the eval script before the app. Then every later change is judged by a number, not by a confident summary.

One step at a time

"Add keyword search and show me the score before and after." A small system that fully works beats a large one that half works.

Ask for plain code first

No framework until you can say what it replaces. Assistants reach for abstractions freely; you are the one who debugs them.

Read every prompt it writes

The prompt is the behaviour of your app. It is the code that matters most and the easiest to skim past.

Make it run things

Library APIs here change every few months, and an assistant's knowledge is older than the libraries. Running beats describing.

Ask "how would this fail?"

It is good at inventing awkward inputs. Turn its answers into test cases.

A true example from this book, which was itself written with an AI assistant. For chapter 16 the assistant first wrote the MCP server with class names from version 1 of the library. Version 2 had renamed them, and the code failed on the first run. It was only caught because every snippet was executed before it went on a page. The same assistant's first router prompt scored 5 out of 8. Running and measuring is what turned plausible code into working code.

The mistakes almost everyone makes once

No eval; judging by trying a few questions.Ten cases and a score, from the first hour.
Blaming the model for a retrieval miss.Print the retrieved chunks first.
Sending everything "to be safe".Fewer, better chunks. More context is slower, dearer and often worse.
Starting with an agent.A workflow; an agent for the one step that needs it.
Letting the model do arithmetic, comparisons or lookups.Code does exact work; the model gets the result.
Trusting the output's structure.Validate everything, like input from the internet.
Treating the prompt as a security control.Permissions and checks in code.
The biggest model everywhere.The smallest that passes the evals, per step.
Editing prompts in place with no version.Prompts in files, in git, evaluated before they ship.
No timeout, no token cap, no spending alert.All three, on day one.

Use it when, skip it when

Are you ready to move on from the first version?

Grow it when

  • The score has stopped improving with prompt changes, and the failures share a cause.
  • Real users are asking things your cases did not cover.
  • You can state the next box's job as "these failing cases will pass".

Stay small when

  • It works for the people using it. Finished is allowed.
  • You are adding something because an article said every serious system has one.
  • You have not yet looked at the failures you already have.

In the docs assistant

Use the book's app as your starting point

The fastest first project is to make the docs assistant answer questions about your documents:

  1. Copy the app folder.
  2. Replace handbook.md with your own text: a heading per document, a paragraph per idea.
  3. Replace the EVAL list in assistant.py with ten questions of yours and the number of the paragraph that answers each.
  4. Run uv run python app/assistant.py --eval. That is your scoreboard.
  5. Run --explain on each question that fails, and start at step 4 of the picture above.

Try it. Today, not next week: do the first hour. Ten inputs, ten good outputs, in a file. Everything else in this book is a way of making that score go up.
