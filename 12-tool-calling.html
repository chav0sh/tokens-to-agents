Tool calling

A model can only write text. Tool calling is the convention that lets it ask your code to do something: look up a record, run a search, send a request. It is the step from "a model that answers" to "a model that can use your systems".

The problem

The answer is in a system, not in a document

Maria asks: "Do I have enough holiday left to take 10 days off?" The handbook says how many days employees get. How many Maria has left is a row in the HR system. Retrieval over documents will never find it, and the model cannot query anything. Something has to call the HR system, and that something is your code.

The picture

The model asks; your code acts

  1. 1. You sendthe question, and a description of each tool
  2. 2. The model repliesnot with text, but with "call this tool with these arguments"
  3. 3. Your code runs itan ordinary function call
  4. 4. You send the resultas one more message
  5. 5. The model answersusing the result

The model never executes anything. It writes a small piece of JSON naming a function and its arguments. Whether that function runs, with which permissions, and what happens if it fails is entirely your code's decision. That is where the safety of the whole system lives.

How it works

A tool is a function plus a description

What the model is given

For each tool: a name, a sentence saying what it is for, and the arguments as a JSON schema. A library builds this from your function's signature and docstring:

@tool
def holiday_days_left(employee: str) -> str:
    """How many paid holiday days an employee has left this year. Needs the employee's full name."""
    ...
name: holiday_days_left description: How many paid holiday days an employee has left this year. Needs the employee's full name. arguments: {"type": "object", "properties": {"employee": {"type": "string"}}, "required": ["employee"]}

The docstring is a prompt. It is the only thing the model knows about the tool, so it decides whether the tool gets called at the right moment.

What the model sends back

Given Maria's question and two tools, this is the model's real reply:

content: '' tool_calls: [{'name': 'holiday_days_left', 'args': {'employee': 'Maria Lind'}, 'id': 'call-6e65…'}] usage: {'input_tokens': 421, 'output_tokens': 28}

No text, one tool call. Note the 421 input tokens for a one-line question: the tool descriptions are sent with every request. Twenty tools with long descriptions is a real cost, and makes the model's choice harder.

The round trip

MessageFromContent
1systemUse the tools to look things up. Never guess a number or a rule.
2userI'm Maria Lind. I want to take 10 days off next month. Do I have enough holiday left?
3assistanttool call: holiday_days_left(employee="Maria Lind")
4toolMaria Lind has 7 holiday days left this year.
5assistant…the answer, or another tool call.

The conversation is still stateless (chapter 1): each request carries all the messages so far, including the tool results.

Three kinds of tool

KindExamplesRisk
ReadSearch, look up a record, query a database, fetch a page.Low. The worst case is a wrong or leaked fact, so check who is allowed to read what.
ComputeA calculator, a date function, running code.Low to medium. This is how you get exact arithmetic out of a system built on a model.
WriteSend an email, create a ticket, change a record, pay.High. A wrong call changes the world. Require confirmation, or keep a person in the loop.

Writing tools the model can use

DoBecause
Name it for what it does: holiday_days_left, not hr_api_v2.The name is part of the prompt.
Say when to use it, and what the arguments must look like."Needs the full name" prevents a call with "Maria".
Few tools, few arguments, simple types.Every option is a chance to choose wrongly.
Return errors as readable text: "No employee called 'Maria'."The model reads the result. Given a clear error it can correct itself; given a stack trace it cannot.
Validate the arguments and check permissions inside the function.The arguments come from a model reading user text. Treat them like any request from the internet.

Use it when, skip it when

A tool or just code?

Use tool calling when

  • The model must decide whether and which lookup is needed, from the user's words.
  • The data is live or per-user: balances, orders, tickets, calendars.
  • The task needs exact computation or an action in another system.

Skip it when

  • You already know the lookup is needed. Call the function yourself and put the result in the prompt: cheaper, faster, and it cannot be skipped. Chapter 13 compares the two.
  • The action is risky and nothing checks it.
  • The model you use handles tools badly. Small models often do; test before you rely on it.

In the docs assistant

Two tools

The assistant gets a lookup into a (made-up) HR system, and its own handbook search wrapped as a tool. They live in app/agent.py.

from langchain_core.tools import tool

HOLIDAY_DAYS_LEFT = {"Maria Lind": 7, "Tom Ek": 18, "Jonas Berg": 3}   # stands in for the HR system

@tool
def search_handbook(question: str) -> str:
    """Search the company handbook. Use for any question about company policy or forms."""
    return "\n".join(f"[{chunk['doc']}] {chunk['text']}" for chunk in retrieve(question))   # chapters 4 to 9

@tool
def holiday_days_left(employee: str) -> str:
    """How many paid holiday days an employee has left this year. Needs the employee's full name."""
    if employee not in HOLIDAY_DAYS_LEFT:
        return f"No employee called {employee!r}."        # an error the model can read and react to
    return f"{employee} has {HOLIDAY_DAYS_LEFT[employee]} holiday days left this year."

model = llm.bind_tools([search_handbook, holiday_days_left])
reply = model.invoke([("system", AGENT_SYSTEM), ("human", question)])
print(reply.tool_calls)

Notice that retrieval itself has become a tool. This is a common design: instead of always searching, the model searches when it judges it needs to, and writes the search query itself.

Try it. With a model key set, run uv run python app/agent.py and read the first block of output. Then change a tool's docstring to something vague ("HR function") and see whether the model still picks it.
