Evals

An eval is a test suite for a system whose output is never exactly the same twice. You have been using one since chapter 4: the scoreboard. This chapter is the full picture: what to test, how to grade open-ended text, and why this is the skill that separates AI engineering from prompt tinkering.

The problem

"It worked when I tried it" is not a test

With ordinary code, you write assert result == expected and you are done. Here the result is a sentence, phrased differently on each run, and "correct" has several parts: is it true, is it complete, does it come from the documents, does it answer the question that was asked?

Meanwhile everything you change moves the output: a word in the prompt, the chunk size, a model upgrade you did not ask for. A change that fixes one question quietly breaks two others. Without a fixed set of cases and a score, you cannot see that, and you end up tuning by feeling.

So write the cases first. Huyen's AI Engineering calls this evaluation-driven development, after test-driven development: decide how the application will be judged before you build it. The cases say what a good answer is; the score says whether a change helped.

Then the same eval was run again

Nothing was changed. The same code, the same prompt, temperature 0, and the invented police report did not appear this time. This is chapter 1's warning in practice: the output of a hosted model can differ between identical calls. Two consequences:

  • One run is a sample. Run an eval several times before trusting a small difference between two scores.
  • A failure that shows up one time in two is still a failure your users will meet.

Test the judge before you trust it

A judge is a prompt, so it gets its own cases: answers you know are wrong. Two were planted:

Planted answerThe judge's verdict
"Full-time employees get 30 days of paid holiday per year."Not supported: "the passage states 25 days."
"You get 25 days of paid holiday, and unused days are paid out in cash."Not supported: "the passage only states they carry over."

What makes a judge prompt work: one criterion per judge, a yes-or-no verdict instead of a 1-to-10 score, and the reason written before the verdict (chapter 2).

Use it when, skip it when

How much eval is enough?

Always

  • A handful of cases and a score, before the first prompt change. Even for a weekend project.
  • Code checks for anything code can check: format, required fields, citations, forbidden content.
  • A rerun before every model or prompt change reaches users.

Add later, when it pays

  • A model as judge, when correctness depends on meaning and you have more cases than you can read.
  • Repeated runs and statistics, when you compare versions that are close.
  • Evals on live traffic, when you have traffic.

In the docs assistant

Two graders in forty lines

def passes_checks(answer: str, phrase: str | None, document: str | None) -> bool:
    """The cheap eval: plain string checks."""
    if phrase is None:                                   # the handbook has no answer: it must say so
        return "don't know" in answer.lower() or "do not know" in answer.lower()
    return phrase.lower() in answer.lower() and document.lower() in answer.lower()

class Verdict(BaseModel):
    reason: str = Field(description="One sentence: which claim is or is not supported.")   # reason first
    supported: bool = Field(description="True only if every claim in the answer is stated in the passages.")

JUDGE_SYSTEM = (
    "You check an assistant's answer against the passages it was given.\n"
    "The answer is supported only if every factual claim in it is stated in the passages.\n"
    'An answer that says it does not know is supported. Ignore the "source" part of the answer.'
)

def judge(passages: str, answer: str) -> Verdict:
    model = llm.bind_tools([Verdict], tool_choice="required")
    reply = model.invoke([("system", JUDGE_SYSTEM), ("human", f"Passages:\n{passages}\n\nAnswer:\n{answer}")])
    return Verdict.model_validate(reply.tool_calls[0]["args"])

Try it. With a model key set, run uv run python app/reliability.py evals twice and compare the two scores. Then fix the false alarm: make passes_checks accept "do not mention" as a refusal, and think about what that loosening might now let through.
