Reference architectures

The docs assistant is one shape of AI product. This chapter applies the method from chapter 22 to four others. None is built here: they are designs on paper, the kind you would bring to a planning meeting. Notice how different they are, and how the same seven questions produce each one.

The problem

"Chat over documents" is not the only AI product

Because RAG chatbots are the usual tutorial, it is easy to see every problem as one. Many of the most useful AI features have no chat window, no retrieval, or no conversation. Recognising the shape of a problem is most of the design.

How it works

The four designs

Each one: the flow, what the user sees, what the model can call, where the data lives, what it costs, and the decisions that matter.

1. A customer support bot answers from the help centre, hands over when it should

  1. Message
  2. Input guard
  3. Routehow-to · my account · upset or unclear
  4. Search help articleshybrid + rerank
    Look up the accountby the logged-in customer
  5. Answerwith a link to the article
  6. Checkreal source? supported?
  7. Reply, or hand off
Interface
A chat widget with a way to reach a person. Staff receive hand-offs with a summary.
Tools
Look up the account or order, open a ticket, hand off.
Database
Help articles in a hybrid search index. Accounts stay in their own system.
Budget
Two small-model calls, about 2 s. $0.000965 per message: about $48 for 50,000 a month.
  • A workflow, not an agent. The kinds of request are known, and cost and behaviour must be predictable in front of customers.
  • Handing off is a designed path, not a failure. Upset customers, unclear requests and answers that fail the check go to a person. A bot that never gives up is the worst support experience.
  • The account lookup uses the session's customer ID, never a name or number typed into the chat. Otherwise anyone can ask about anyone.
  • Eval: past tickets with their correct resolution. Measure "would this have resolved it?" and, separately, "did it hand off when it should?".

2. Document extraction reads incoming invoices, produces records for accounting

  1. PDF arrivesin a queue
  2. Get the textparser or OCR
  3. Extractstructured output: supplier, date, lines, totals
  4. Validate in codelines add up? date sane? supplier known?
  5. Save the recordchecks passed
    Review queuea person corrects it
Interface
None for most documents. A review screen for the ones that fail a check.
Tools
None. A batch pipeline, like any import job.
Database
Your accounting database. No vector index, no graph.
Budget
One small-model call per document, nobody waiting. $0.00135 per invoice: $27 for 20,000 a month.
  • No chat, no retrieval, no agent. One document in, one record out.
  • The schema is the prompt. Field names and descriptions tell the model what to find. Structured output guarantees the shape, not the values.
  • Arithmetic and lookups are code. "Do the lines sum to the total?" and "is this supplier known?" are exact checks that catch most model mistakes for free.
  • Corrections become eval cases. The eval is field-by-field accuracy against a few hundred hand-checked invoices.

3. Questions to SQL "what was revenue per region last quarter?"

  1. Question
  2. Find the tablessearch table and column descriptions
  3. Write the SQLschema + example queries in the prompt
  4. Validateparses? SELECT only? allowed tables?
  5. Run itread-only, replica, timeout
  6. Showthe table, and the query
Interface
A question box in a dashboard or chat. It shows the result and the SQL that produced it.
Tools
One: run a query, as a read-only user.
Database
The SQL database you have. A small search index over table and column descriptions.
Budget
One large-model call. $0.012 per question: $60 for 5,000 a month.
  • Retrieval is over the schema, not the data. Good column descriptions matter more than the model.
  • Permissions are the control. The query is written by a model from a stranger's text, so the database user can only read, on a replica, with a time limit.
  • The query is shown. A wrong join gives a believable wrong number. Showing the SQL lets someone check it.
  • One retry on a database error, with the error in the prompt. A small evaluator loop (chapter 13).
  • Eval: compare the rows, not the SQL text. Many different queries are correct.

4. An agent that acts an IT helpdesk: "I can't get on the VPN"

  1. Request
  2. Model: what next?
  3. Read toolsuser, device, past tickets, runbooks
    Write toolsonly after a person confirms
  4. Back to the modeluntil done, or a step limit
  5. Summarywhat was done, and the log
Interface
A chat that shows what it is doing and asks before it changes anything.
Tools
Read: look up user, device, tickets; search runbooks. Write: reset access, grant a licence, open a ticket.
Database
The systems it acts on, plus a log of every tool call. Runbooks in a search index.
Budget
About six large-model calls. $0.09 per request: $180 for 2,000 a month, and tens of seconds each.
  • An agent, because the steps depend on what it finds. A VPN problem may be an expired password, a missing group or a broken device.
  • Read tools are free to use; write tools stop for confirmation. Looking things up is safe to get wrong. Changing access is not.
  • A short allow-list of actions, each with narrow permissions. The agent can do exactly what its tools allow, whatever any text tells it (chapter 18).
  • A ceiling on steps and spend, and every tool call logged: the audit trail and the only way to debug it.
  • Eval: scripted scenarios in a test environment. Judge the end state and the path: no forbidden action, not too many steps.

Costs use the example prices from chapter 3 ($0.30 and $2.50 per million tokens for the small model, $3 and $15 for the large) and assumed token counts. The agent is by far the most expensive per use, and the hardest to test.

Use it when, skip it when

Which shape is yours?

Recognise the shape by

  • Someone asks, facts are in documents: design 1 and the docs assistant.
  • A document or message comes in, a record goes out: design 2. Also classification and routing of tickets or emails.
  • Language in, a formal language out (SQL, a search filter, a config): design 3.
  • A goal, and several systems to act in: design 4.

Common mis-shapes

  • A chat window on top of what should be a form with one smart field.
  • RAG over data that lives in tables. That is design 3 or a plain report.
  • An agent where the steps are the same every time. That is a pipeline.
  • One giant prompt doing extraction, judgement and writing. Split it into steps you can test.

In the docs assistant

Where the book's app sits among them

The docs assistant is closest to design 1 without the hand-off, with a small piece of design 4 inside it (the HR lookup as a tool). It contains no extraction pipeline and no generated queries: the Cypher in chapter 11 is fixed and written by hand, exactly because generated queries are design 3's risk.

Everything in these four designs is assembled from parts you have run. What changes is the arrangement, and where the checks stand.

Try it. Pick the design nearest to something you want to build and change one requirement: ten times the volume, or a wrong output that costs real money. Which box changes?
