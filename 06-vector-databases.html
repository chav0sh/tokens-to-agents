Vector databases

A vector database stores embeddings and answers one query fast: "which stored vectors are nearest to this one?" It is an index type you have not used before, wrapped in a database you would recognise.

The problem

Comparing with everything is a full table scan

Chapter 5 compared the question with all 14 chunks. That is exact, and fine for thousands of vectors. At ten million chunks it means ten million cosine calculations per question. A B-tree cannot help: it sorts along one dimension, and a vector has hundreds, with no single order that keeps neighbours together. You need an index built for "near", not for "equal" or "less than".

The picture

HNSW: express lanes over a graph of neighbours

The index most vector databases use is HNSW (hierarchical navigable small world). Every vector is linked to a few of its nearest neighbours. On top sit thinner layers holding fewer vectors with longer links. It is a skip list, in many dimensions.

A sketch, flattened to one dimension. The search starts at the top, moves greedily towards the query, and drops a layer whenever no neighbour is closer. It touches a handful of points instead of all of them.

The price is in the name of the family: approximate nearest neighbour (ANN) search. The greedy walk usually finds the true nearest vectors, not always. You trade a little recall for a very large speed-up, and the index's settings move that trade.

How it works

A point is three things

PartWhat it isLike
IDYour key for the chunk.A primary key.
VectorThe embedding. The only part that is indexed for "near".An indexed column.
PayloadJSON you get back with a hit: the text, the document title, a date, who may read it.The other columns.

A collection holds points of one vector size, compared with one distance (cosine, dot product or Euclidean). Use the distance the embedding model was trained for; for most text models that is cosine.

Filters: the WHERE clause

Real searches are "nearest to this vector and department = HR and the user may read it". A vector database applies the payload filter during the graph walk. Filtering afterwards is a trap: ask for the top 5, filter out 4 the user may not see, and you are left with one result.

The other index families, in one line each

NameIdeaYou meet it
Flat (exact)Compare with everything.Small collections, and as the reference when measuring recall.
HNSWA layered graph of neighbours.The default almost everywhere.
IVFCluster the vectors; search only the nearest clusters.FAISS, pgvector's ivfflat.
QuantizationStore each vector compressed, with fewer bits.A memory-saving setting on top of the others.

How big is it?

One vector of 384 numbers at 4 bytes each is 1,536 bytes. So:

The docs assistant, 14 chunks: 22 KB.
A 200-page handbook, about 380 chunks: 0.6 MB.
One million chunks: 1,000,000 × 1,536 bytes = 1.5 GB of vectors, before the index's links and the payloads.

HNSW lives in memory for speed, so the last line is a RAM budget. That is where quantization and smaller embedding models start to matter.

Use it when, skip it when

Do you need a new database?

Use a vector database when

  • You have more vectors than a loop handles comfortably: roughly a hundred thousand and up.
  • You need filters, updates and deletes, and the index must survive a restart.
  • Several services search the same vectors.

Skip it when

  • A few thousand chunks: keep the vectors in memory and loop. It is exact and has no moving parts.
  • You already run Postgres: the pgvector extension adds a vector column and an HNSW index to the database you have.
  • You already run Elasticsearch or OpenSearch: both have vector search built in.

The tools

The names in this slot

KindCommon namesNotes
Dedicated, open sourceQdrant (this book) · Weaviate · Milvus · ChromaQdrant is one Docker container or one cloud URL, with strong payload filters. Chroma is the lightest for prototypes.
Dedicated, managed onlyPineconeNothing to run; pay per use.
Inside a database you havepgvector (Postgres) · Elasticsearch / OpenSearch · Redis · MongoDB AtlasOne less system to operate. Often the right first choice.
A library, not a databaseFAISS · hnswlibJust the index, in your process. No server, no filters, no persistence unless you add them.

They all do the same core job. Choose on what you already operate, on filtering needs and on scale, not on benchmark charts.

In the docs assistant

The chunks move into Qdrant

from qdrant_client import QdrantClient
from qdrant_client.models import Distance, PointStruct, VectorParams

qdrant = QdrantClient(":memory:")        # for tests; in production: QdrantClient(url="http://qdrant:6333")

# Indexing: once, and again whenever the documents change.
qdrant.create_collection("docs", vectors_config=VectorParams(size=384, distance=Distance.COSINE))
qdrant.upsert("docs", points=[
    PointStruct(id=chunk["id"], vector=vector, payload=chunk)      # payload: {"id", "doc", "text"}
    for chunk, vector in zip(CHUNKS, chunk_vectors)
])

# Answering: embed the question, ask for the nearest three.
hits = qdrant.query_points("docs", query=question_vector, limit=3).points
for hit in hits:
    print(hit.id, round(hit.score, 2), hit.payload["doc"])
8 0.73 Security policy 10 0.52 Onboarding guide 12 0.51 HR forms

":memory:" runs the same API inside your process, so tests need no Docker. The collection's size must match the embedding model; a mismatch is an error at insert time, not a silent bug.
