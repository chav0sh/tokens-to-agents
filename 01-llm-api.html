The LLM as an API

A large language model (LLM) is a service you send text to and get text back from. This chapter is what a back-end developer needs to know about that one call: what goes in, what comes out, what you pay for, and why the same request can give two different answers.

The problem

It looks like any other API. It isn't.

You have called a thousand HTTP APIs. This one breaks four habits:

You expectWith a model
Same input, same outputThe output is picked with some randomness. Two calls can differ.
Priced per requestPriced per token, in and out. A long prompt costs more than a short one.
Send any payload sizeEverything must fit in the context window: a hard limit on tokens.
A typed responseFree text, unless you ask for a structure and check it.

The picture

One token at a time

A model does one thing: given some text, it scores every possible next piece of text. Your "answer" is that step repeated in a loop.

A 150-token answer is 150 trips round this loop. That is why long answers are slow, and why output tokens cost more than input tokens.

How it works

Tokens, the window, and the dice

1. Text becomes tokens

A token is a piece of a word. Common words are one token; rare words, codes and other languages are cut into several. These are real splits from one widely used tokenizer:

How many days of parental leave do I get?

9 words → 10 tokens

Unbelievably, form HR-2291 was misfiled.

5 words → 14 tokens. Codes and unusual words are expensive.

Hur många dagars föräldraledighet får jag?

The same question in Swedish: 6 words → 12 tokens.

Rule of thumb: in English, 100 tokens is about 75 words. Every model family has its own tokenizer, so counts differ between models. To know, count with the model's own tokenizer, or read the token usage the API returns.

2. Everything shares one window

The context window is the most tokens a model can handle in one call: your instructions, the documents you paste in, the question, and the answer. Here is an 8,000-token window, filled:

Documents 6,300
free 850
  • Instructions 300
  • Documents 6,300
  • Question 50
  • Reserved for the answer 500

Windows today run from a few thousand to millions of tokens. Bigger is not free: you pay for every token you send, and models use the middle of a long prompt less well (chapter 2).

The API is also stateless. The model remembers nothing between calls. A "conversation" is your code sending the whole history again each time, as a list of messages with roles: system (your rules), user (the person) and assistant (the model's earlier replies). It is like HTTP without a session: the client carries the state.

3. The next token is picked by weighted dice

Take the text "Employees get 12 weeks of parental". The model scores every token in its vocabulary; here are five of them. The scores become probabilities, and one token is drawn. Two settings change the draw. Move them:

1.0 1.00

SettingWhat it doesTypical use
TemperatureDivides the scores before they become probabilities. Low sharpens the favourite; high flattens the field. At 0 the model always takes the top token.0 for extraction, classification and evals. Higher for writing and ideas.
Top-pKeeps the smallest set of tokens whose probabilities add up to p, and drops the rest. Cuts the unlikely tail.0.9 to 0.95, or leave the default.
Top-kKeeps only the k most likely tokens.Mostly a default you don't touch.
Max output tokensStops the loop after N tokens. A cut-off answer is a symptom of this limit.Always set it: it caps cost and runaway answers.

Temperature 0 is not a guarantee. It makes answers as repeatable as the provider allows, not identical forever: hardware, batching and silent model updates can still change a result. Design for an output that may vary, and test with evals (chapter 17), not with string equality.

4. Text out, unless you ask for a structure

Your code wants fields, not prose. Three levels, from weakest to strongest:

LevelHowWhat can go wrong
Ask in the prompt"Answer as JSON with keys …"Extra text around the JSON, a missing key, broken syntax.
JSON modeAn API switch: the output is valid JSON.Valid JSON, but maybe not your shape.
Structured outputYou pass a schema; the provider limits each token to what the schema allows.The shape is right. The values can still be wrong.

Whatever the level, treat the output like user input from the internet: parse it, validate it, and decide what happens when it fails.

Use it when, skip it when

Is a model call the right tool?

Use a model when

  • The input or output is language: questions, documents, summaries, emails.
  • The input is messy and rules would never cover it.
  • A wrong answer now and then is acceptable, or you can check the answer.

Skip it when

  • A query, a regex or an if does the job. That is cheaper, faster and exact.
  • You need arithmetic or an exact lookup. Do it in code and give the model the result.
  • The answer must be identical every time, or arrive in a few milliseconds.

In the docs assistant

Version 1: one call

The first version of the assistant is a single request. We paste the policy sentence in by hand, because nothing finds documents yet.

from langchain_nvidia_ai_endpoints import ChatNVIDIA   # any LangChain chat model has this interface

llm = ChatNVIDIA(
    model="nvidia/nemotron-3.5-lightning-30b-a3b",
    temperature=0,               # the most likely token every time: repeatable
    max_completion_tokens=200,   # cap the answer, and the bill
    timeout=60,                  # a hung call fails instead of freezing the request
)

reply = llm.invoke([
    ("system", "You answer questions about company policy in one sentence."),
    ("human", "Policy: employees get 12 weeks of paid parental leave.\n\nHow long is parental leave?"),
])
print(reply.content)
print(reply.usage_metadata)
12 weeks {'input_tokens': 45, 'output_tokens': 4, 'total_tokens': 49}

Real output from one run, 0.8 seconds. The key comes from the environment, never from the code.

About the library. ChatNVIDIA comes from LangChain, which this book uses for one thing so far: a common interface over model providers. Swap the class for ChatOpenAI, ChatAnthropic or ChatGoogleGenerativeAI and the rest of the code stays the same. Chapter 14 covers what else LangChain does.

The same call, as a typed object

from pydantic import BaseModel, Field

class Answer(BaseModel):
    answer: str = Field(description="One sentence")
    weeks: int = Field(description="Length of the leave in weeks")
    source: str = Field(description="The policy sentence the answer is based on")

result = llm.with_structured_output(Answer).invoke(
    "Policy: employees get 12 weeks of paid parental leave.\n\nHow long is parental leave?"
)
Answer(answer='12 weeks', weeks=12, source='Policy: employees get 12 weeks of paid parental leave.')

The schema is a pydantic model: think of a Go struct with tags, or a NestJS DTO. The field descriptions are part of the prompt, so write them for the model.

What a call costs

Cost is tokens times price. Prices are quoted per million tokens, with output several times dearer than input. With example prices of $0.30 in and $2.50 out, a realistic request of 1,200 prompt tokens and a 150-token answer costs:

1,200 × $0.30 ÷ 1,000,000 + 150 × $2.50 ÷ 1,000,000 = $0.000735
10,000 questions a day: $7.35 a day.

The example prices are made up to show the sum; check your provider's price page. The lesson holds: the prompt is usually most of the tokens, the answer is most of the waiting.

Try it. Get an API key from any provider (several have a free tier), run the first snippet, and print usage_metadata. Then ask the same question five times at temperature 1 and compare the answers.
