Graph databases

A graph database stores things and the connections between them, and makes "follow the connections" the cheap operation. This chapter is the database itself: the model, the query language, and when it beats the SQL you already know. The next chapter plugs it into the assistant.

The problem

Some answers are in the connections, not in the text

Maria asks: "Who has to approve my expense claim of 800 euros?" The search finds the right rule: "Expense claims above 500 euros need a director's approval." Correct, and useless to Maria. She wants a name. Which director? The one above her, which depends on who her manager is, and who that manager reports to. No chunk of the handbook says so. It is in the org chart.

You can store an org chart in SQL: an employees table with a manager_id. One level up is a self-join. "Everyone above Maria" needs a join per level, and you don't know how many levels there are:

-- SQL: everyone above Maria, however deep the chain is
WITH RECURSIVE chain AS (
    SELECT manager_id, 1 AS levels_up FROM employees WHERE name = 'Maria Lind'
  UNION ALL
    SELECT e.manager_id, chain.levels_up + 1
    FROM employees e JOIN chain ON e.id = chain.manager_id
    WHERE e.manager_id IS NOT NULL
)
SELECT e.name, e.title, chain.levels_up
FROM chain JOIN employees e ON e.id = chain.manager_id ORDER BY levels_up;
// Cypher, the graph query language: the same question
MATCH path = (:Person {name: 'Maria Lind'})-[:REPORTS_TO*]->(boss:Person)
RETURN boss.name, boss.title, length(path) AS levels_up ORDER BY levels_up

Both work. The second one reads like the question, and stays that short when the question grows to three kinds of connection.

The picture

Nodes and relationships

Part of the docs assistant's org chart, as it is stored. The picture on the whiteboard and the data in the database are the same shape. That is the appeal.

PieceWhat it isIn SQL terms
NodeA thing: a person, a team, a document.A row.
LabelThe kind of node: Person, Team.The table name.
RelationshipA named, directed connection between two nodes: REPORTS_TO.A foreign key or a join-table row, but stored as a direct link.
PropertyA key and value on a node or on a relationship: title: 'CEO'.A column.

How it works

Cypher: you draw the pattern you are looking for

A Cypher query is a small drawing in text. Round brackets are nodes, square brackets inside an arrow are relationships:

(a:Person)-[:REPORTS_TO]->(b:Person) a reports to b (a)-[:REPORTS_TO*]->(b) a reports to b through any number of steps (a)-[:MEMBER_OF]->(team)<-[:MEMBER_OF]-(c) a and c are in the same team

MATCH finds every place in the graph where the drawing fits. WHERE filters, RETURN picks what comes back: the same roles as in SQL.

Four questions, run on the org chart

QuestionPatternResult
Who does Maria report to?(:Person {name: $name})-[:REPORTS_TO]->(boss)Jonas Berg, Engineering Manager

Real results from Neo4j. The star, *, is the part SQL finds hard: "any number of steps".

Why following connections is cheap

In a relational database, a join looks rows up through an index, and each extra hop is another lookup against the whole table. A graph database stores, with each node, direct references to its relationships. Going from Maria to her manager is following a pointer. The cost of a query depends on how much of the graph it walks through, not on how big the whole graph is.

Parameters, always. $name is a query parameter, sent separately from the query text. Building Cypher by gluing a user's text into a string is the same injection hole as in SQL.

Use it when, skip it when

A graph database is a specialist

Use one when

  • The questions are about paths: who is connected to whom, through what, how far away.
  • The depth is unknown or large: reporting lines, dependencies, permissions inherited through groups.
  • There are many kinds of connection and you keep adding more.
  • Typical cases: org charts, access control, fraud rings, recommendations, supply chains, knowledge graphs.

Skip it when

  • The data is tables and the questions are sums and filters. That is what SQL is best at.
  • One or two joins answer everything.
  • The hierarchy is small and simple: a recursive query in the Postgres you already run will do.
  • You only want it because "knowledge graph" sounds good. It is one more database to operate.

In the docs assistant

The org chart goes into Neo4j

The org chart is a ten-line CSV, app/org.csv: name, title, team, reports_to. Loading it is two queries:

from neo4j import GraphDatabase

driver = GraphDatabase.driver("bolt://localhost:7688", auth=("neo4j", "tokens-to-agents-local"))

def load_org_chart() -> None:
    rows = list(csv.DictReader(open("org.csv", encoding="utf-8")))
    with driver.session() as session:
        session.run("MATCH (n) DETACH DELETE n")                       # start clean
        session.run("""
            UNWIND $rows AS row
            MERGE (p:Person {name: row.name}) SET p.title = row.title   // MERGE = create if missing
            MERGE (t:Team {name: row.team})
            MERGE (p)-[:MEMBER_OF]->(t)
            """, rows=rows)
        session.run("""
            UNWIND $rows AS row
            MATCH (p:Person {name: row.name}), (m:Person {name: row.reports_to})
            MERGE (p)-[:REPORTS_TO]->(m)
            """, rows=[row for row in rows if row["reports_to"]])

def query(cypher: str, **parameters) -> list[dict]:
    with driver.session() as session:
        return [record.data() for record in session.run(cypher, **parameters)]

UNWIND $rows turns the list parameter into rows, like a bulk insert. MERGE makes the load safe to run twice.

Try it. Start a throwaway Neo4j, then run the examples:

  2. uv run python app/graph.py loads the org chart and prints the four results above.
