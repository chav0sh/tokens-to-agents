GraphRAG

GraphRAG means using a graph as a source of context for the model, next to or instead of text search. The word covers several different designs. This chapter builds the simplest and most common one, and maps the others.

The problem

The search finds the rule. Nobody resolves it.

"I'm Maria Lind. Who has to approve my expense claim of 800 euros?" The assistant from chapter 8 retrieves the right chunk and answers:

Your expense claim of 800 euros needs a director's approval. [Expenses policy]

Faithful to the handbook, and no help. The rule speaks of a role; the person filling that role for Maria is a fact about relationships, stored in the graph from chapter 10. Text search cannot produce it, because no text says it.

The picture

A second retriever, for facts about connections

  1. Question
  2. Search the textchunks, as before
    Query the graphwho is mentioned? what is connected to them?
  3. Build the promptchunks + graph facts
  4. Model
  5. Answer

The graph is not a replacement for the search. The text gives the rule, the graph gives the people; the prompt needs both.

How it works

Three attempts at one question

The steps: find the people named in the question, ask the graph about them, and add the results to the prompt as passages marked [Org chart]. What exactly you add turns out to matter a great deal. These are real answers from the same small model.

AttemptGraph facts added to the promptThe model's answer
1. No graphNone."…needs a director's approval."
Right, without a name.
2. The whole chainMaria Lind is Engineer. Their manager is Jonas Berg, Engineering Manager. 2 levels above them is Sara Holm, Director of Engineering. 3 levels above them is Erik Dahl, CEO."…Erik Dahl or Sara Holm would need to approve it…"
Wrong: the CEO is not a director, and "or" is not an answer.
3. The resolved factFor Maria Lind, "a director" means Sara Holm (Director of Engineering)."…Based on the org chart, 'a director' means Sara Holm (Director of Engineering)."
Right.

Attempt 2 handed the model raw data and left the reasoning to it: walk up the chain, find the first director. A small model did that badly. Attempt 3 let the database do the walking, with the "nearest director" query from chapter 10, and phrased the result in the handbook's own words. The same phrasing answered four out of four different employees' questions correctly.

Let each part do what it is good at. Exact questions about structure belong in a query: the database is never "roughly right" about who reports to whom. The model's job is to read the rule, read the finished fact, and write the sentence. The less it has to work out, the less it gets wrong.

The four things people call GraphRAG

DesignHow it worksGood forThe cost
Graph lookup (this chapter)Your code spots the entities in the question and runs fixed, tested queries about them.Known kinds of question over a graph you already have.You write one query per kind of fact.
Text-to-CypherThe model writes the Cypher query from the question; your code runs it.Open-ended questions over a graph.The model can write a wrong or harmful query. Use a read-only user, validate, and expect misses.
A knowledge graph built from documentsAt indexing time, a model reads every chunk and extracts entities and relationships into a graph. Retrieval then follows links between chunks.Questions that span documents: "what else is this supplier involved in?"A model call per chunk to build it, and the extraction makes mistakes.
Microsoft's GraphRAGThe same extraction, then the graph is clustered into communities and each community gets a written summary. Broad questions are answered from the summaries."What are the main themes in these 5,000 documents?", which no single chunk can answer.The most expensive index of the four. Worth it only for those broad questions.

When someone proposes "GraphRAG", ask which of the four they mean. They differ by an order of magnitude in cost and effort.

Use it when, skip it when

Is a graph worth adding?

Add a graph when

  • Answers depend on who or what is connected: reporting lines, ownership, dependencies, board seats.
  • You can point at failing questions where the right chunk was retrieved and the answer was still incomplete.
  • The structured data already exists somewhere: an HR system, a CRM, a config database.

Skip it when

  • The answers are in the text. Better search (chapters 5 to 9) is far cheaper.
  • The "graph" is one lookup: a dictionary or a SQL query gives the same fact.
  • You would have to build the graph from documents and have no questions that need it yet.

In the docs assistant

Graph facts become one more kind of passage

MANAGER = "MATCH (:Person {name: $name})-[:REPORTS_TO]->(boss) RETURN boss.name AS name, boss.title AS title"
NEAREST_DIRECTOR = """
    MATCH path = (:Person {name: $name})-[:REPORTS_TO*]->(boss:Person)
    WHERE boss.title STARTS WITH 'Director'
    RETURN boss.name AS name, boss.title AS title ORDER BY length(path) LIMIT 1
"""

def people_in(question: str) -> list[dict]:
    """The employees a question mentions by name."""
    people = query("MATCH (p:Person) RETURN p.name AS name, p.title AS title")
    return [person for person in people if person["name"].lower() in question.lower()]

def graph_facts(question: str) -> list[str]:
    """The database answers the structural question; the fact is phrased in the policy's own words."""
    facts = []
    for person in people_in(question):
        name = person["name"]
        for boss in query(MANAGER, name=name):
            facts.append(f'For {name}, "their manager" means {boss["name"]} ({boss["title"]}).')
        for boss in query(NEAREST_DIRECTOR, name=name):
            facts.append(f'For {name}, "a director" means {boss["name"]} ({boss["title"]}).')
    return facts

passages  = [f"[{chunk['doc']}] {chunk['text']}" for chunk in retrieve(question)]      # chapters 4 to 9
passages += [f"[Org chart] {fact}" for fact in graph_facts(question)]                 # new

Finding the person by looking for their name in the question is the crudest possible method, and enough here. In a real system the name comes from the login, not from the text, which is also safer: people should not get answers about someone else by typing a name.

No scoreboard change. The 12 test questions are all answered from the handbook, so they still score 12/12. Graph questions need their own test cases; the four used above were checked by reading the answers. Chapter 17 turns that into a proper eval.

Try it. With Neo4j running and a model key set: uv run python app/graph.py "I'm Tom Ek. Who do I ask if I want to work from home on Fridays?" prints the answer three ways. Then add a rule to the handbook that mentions "the CEO" and a fact for it.
