The questions

The model and its prompt

Q1What happens when you call an LLM API?Ch. 1
They check
That you see a model as a next-token loop with a bill, not as a database that knows things.
Answer
  1. The prompt is split into tokens, pieces of words, and the model scores every possible next token.
  2. One token is drawn from those scores, added to the text, and the loop repeats until a stop token or the length limit.
  3. Prompt and answer share one context window, and you pay per token in and out, so long answers are slow and costly.
  4. The API is stateless: a "conversation" is your code sending the history again on every call.
Follow-up
"Why is a 150-token answer slower than a 10-token one?" Each token is one more trip round the loop.
Avoid
"The model looks the answer up." It continues text; facts it was not given are guesses.

Q2What do temperature and top-p do, and what would you set them to?Ch. 1
They check
That you know why the same prompt gives different answers, and how to make a test repeatable.
Answer
  1. Temperature divides the scores before they become probabilities: low sharpens the favourite, high flattens the field; at 0 the model takes the top token.
  2. Top-p keeps the smallest set of tokens whose probabilities add up to p and drops the unlikely tail.
  3. Temperature 0 for extraction, classification and evals; higher for writing and ideas; top-p around 0.9 to 0.95, or the default.
Follow-up
"Is temperature 0 fully repeatable?" Not guaranteed: chapter 17 reran the same eval and got different results.
Avoid
Treating temperature as a quality knob. It changes variety, not knowledge.

Q3How do you structure a production prompt?Ch. 2
They check
That a prompt is a document your code assembles and versions, not a sentence typed once.
Answer
  1. Fixed parts first: instructions (role, rules, the way out), then examples; then the parts that change per request: the retrieved context and the question; then a short refocus.
  2. Order matters: models use the start and the end of a prompt best, so rules go first and are repeated last.
  3. Say exactly what you want, including length and format; mark where each part starts and ends; give a way out: "if the passages don't answer, say so".
  4. Prompts are code: files, version control, a version number, and an eval run on every change.
Follow-up
"A prompt change fixed one case and broke another. How would you have known?" Only an eval shows it.
Avoid
Editing a prompt in place on a server.
Learn it
Chapter 2
Q4How do you choose a model for a task?Ch. 3
They check
That you decide with your own data and three dials, not with a leaderboard.
Answer
  1. Hard limits first: may the data leave your network, licence, where it may run. That decides hosted API or self-hosted.
  2. Shortlist two or three, starting small and cheap; public benchmarks only build the shortlist.
  3. Run your own evals on quality, cost and latency; you can pick two and a half of the three.
  4. If it is not good enough, fix the prompt and the context first; move up a model size last. Keep the model behind one function so it is a one-line change.
Follow-up
"Where does the time go in a call?" Time to the first token plus tokens out divided by speed.
Avoid
"I'd use the top model on the leaderboard." It does not know your task, and it is often ten times the price.

Chapter 3

Giving the model context

Q5What is RAG, and when would you not use it?Ch. 4
They check
That you know the two pipelines and that retrieval, not the model, is where RAG usually fails.
Answer
  1. Retrieval-augmented generation: find the passages that answer the question, put them in the prompt, and let the model write an answer that cites them.
  2. Two pipelines: indexing (split, embed, store) when documents change; answering (retrieve, augment, generate) on every question.
  3. Use it when the facts are in your documents and change. Skip it when everything fits comfortably in the prompt, when the answer is a number from a database (a query or a tool), or when the task needs no outside facts.
Follow-up
"An answer is wrong. Where do you look first?" Print the retrieved chunks. If the answer is not in them, no prompt will save it.
Avoid
Blaming the model before checking retrieval.
Learn it
Chapter 4
Q6What is an embedding, and what does a similarity score tell you?Ch. 5
They check
That you can explain search by meaning, and that you do not trust a score threshold blindly.
Answer
  1. An embedding is a list of numbers that represents a text, so that similar meanings get nearby numbers; "time off for a new baby" lands near "parental leave" with no shared word.
  2. Cosine similarity compares two embeddings: 1 means the same direction.
  3. Read the order, not the number: in this book unrelated chunks scored up to 0.59, tying with the right one. A score means different things for different models.
Follow-up
"Where do embeddings fail?" Exact codes and names: FIN-140 and FIN-401 look like twins.
Avoid
A fixed cut-off like 0.7 without measuring it on your own data.
Learn it
Chapter 5
Q7Vector search or keyword search? Why do teams use both?Ch. 7, 8
They check
That you know each search's blind spot, and that you add stages because an eval asked for them.
Answer
  1. Keyword search (BM25 over an inverted index) wins on exact terms: codes, names, rare words. Vector search wins on paraphrases.
  2. Hybrid runs both and merges the lists, usually with reciprocal rank fusion, which needs only ranks, not comparable scores.
  3. A reranker then reads the question and each candidate together and orders them: retrieve wide, rerank narrow.
  4. On this book's twelve questions: keyword 7, vector 11, fused 8, fused and reranked 12.
Follow-up
"Fusion scored lower than vector alone. Why keep it?" It puts the right chunk among the candidates; the reranker then picks it.
Avoid
Adding hybrid and reranking with no eval. Every stage is more code, latency and tuning.
Learn it
Chapter 7, chapter 8
Q8How do you chunk documents?Ch. 9
They check
That you see the trade-off and tune it with a measurement.
Answer
  1. Smaller chunks search sharper but may lose the surrounding sentences; larger ones carry context but blur several topics into one vector, and fewer fit in the prompt.
  2. Split by the document's own structure where it has one (headings, sections), and store labels next to the text: source, title, date.
  3. A few hundred tokens is a common start; change it and rerun the scoreboard. Re-index when documents change.
Follow-up
"How many chunks is a 200-page handbook?" About 133,000 tokens: 400-token chunks with a 50-token overlap make about 381 chunks, and three of them, 1,200 tokens, go into each prompt.
Avoid
"There is a best chunk size." It depends on your documents and questions.
Learn it
Chapter 9
Q9When would you add a graph database or GraphRAG?Ch. 10, 11
They check
That you can tell a question about connections from a question about text.
Answer
  1. When the answer depends on who or what is connected to what, several hops away: "who approves my expenses?" needs the org chart, not a passage.
  2. A graph stores nodes and relationships, and following a connection is cheap; Cypher lets you draw the pattern you want.
  3. GraphRAG means several things; the simplest is a fixed graph lookup whose result goes into the prompt as one more passage.
  4. Skip it when the answers are in the text, or one SQL join would do.
Follow-up
"Could SQL do it?" Yes, with a recursive query; a graph pays off when the walks get deep or varied.
Avoid
Building a knowledge graph from all documents before you have a question that needs it.
Learn it

Building the flow

Q10How does tool calling work, and how do you make tools safe?Ch. 12
They check
That the model only asks, your code acts, and tool input is untrusted.
Answer
  1. You give the model a function's name, description and argument schema; it replies with a name and arguments; your code runs the function and sends the result back.
  2. Few tools, few simple arguments; say when to use each and what the arguments look like.
  3. Return readable errors ("No employee called 'Maria'") so the model can correct itself.
  4. Validate arguments and check permissions inside the function: they come from a model reading user text.
Follow-up
"When is a tool the wrong choice?" When you always need the lookup: call it in code.
Avoid
Letting the model's arguments reach a database without checks.
Learn it
Chapter 12
Q11Workflow or agent: how do you decide?Ch. 13
They check
The most important design choice in an AI system, and whether you default to the simpler one.
Answer
  1. In a workflow your code decides the steps; in an agent the model decides, in a loop.
  2. Use a workflow when you can draw the steps, when cost and behaviour must be predictable, and when some rules must not be skipped. Most business tasks qualify.
  3. Reach for an agent when the steps cannot be known in advance and a wrong step is cheap to notice and undo.
  4. An agent always needs a ceiling: a maximum number of steps, a time limit, a spending limit; write actions behind a confirmation.
Follow-up
"How do you test a router?" As a classifier, with its own labelled questions: in this book a bare prompt sorted 5 or 6 of 8 right, and defining each kind with three examples made it 7 of 8.
Avoid
"Agents are the future, so I'd build an agent."

Q12Why use LangGraph or LangChain instead of plain code?Ch. 14, 15
They check
That you can name what a framework buys and what it costs.
Answer
  1. LangChain gives one interface per kind of part, so switching providers or vector stores is a small change; take the interfaces, be careful with deep abstractions.
  2. LangGraph models a flow as state, nodes and edges. It earns its place when the flow has to wait or retry: a checkpointer saves the state after every step, so a run can pause for a person and resume, and loops are just edges.
  3. For a straight path, a plain function is easier to read and debug.
Follow-up
"What does a node return?" Only the keys it changed; the graph merges them into the state.
Avoid
Starting with a framework before you know your flow.
Learn it

Q13How does conversation memory work, and what is MCP?Ch. 16
They check
That memory is state you send again, and MCP is a plug, not intelligence.
Answer
  1. The model forgets between calls; memory is your code storing the conversation under an ID and sending the relevant part again.
  2. History grows, and the window and the bill grow with it, so keep the last turns or a summary.
  3. MCP, the Model Context Protocol, is an open standard from late 2024: a server offers tools, data and prompts; a client in your app discovers and calls them. It does for AI tools what the Language Server Protocol did for editors.
Follow-up
"Does MCP make tools safe?" No: the same rules apply inside each tool.
Avoid
"The model remembers the user."
Learn it
Chapter 16

Keeping it reliable

Q14How do you evaluate an LLM application?Ch. 17
They check
The skill that separates AI engineering from prompt tinkering.
Answer
  1. A fixed set of cases with what a good output looks like, run on every change, giving one score: a test suite whose result moves.
  2. Test each part, then the whole: did retrieval find the chunk, did the router pick the branch, is the final answer right.
  3. Three graders: code checks (free, exact, narrow), a model as judge (understands meaning, costs a call, can be wrong), a person (the ground truth, slow).
  4. Cases come from real questions, past failures and questions the documents cannot answer.
Follow-up
"How many cases?" Start with ten real inputs and the outputs you would accept, before the first prompt change; add every failure you find.
Avoid
"I tried it and it worked."
Learn it
Chapter 17
Q15Can you trust an LLM as a judge?Ch. 17
They check
That you test the judge before you trust it.
Answer
  1. A judge is a prompt, so it gets its own cases: answers you know are wrong, planted to see if it catches them.
  2. One criterion per judge, a yes-or-no verdict instead of a 1-to-10 score, and the reason written before the verdict.
  3. Use code checks for what code can check; use the judge for meaning, like "is every claim supported by the passages?"
Follow-up
"Your two graders disagree. Which do you believe?" Neither by default: in this book both scored 13 of 14 but failed different cases. Read the cases where they differ.
Avoid
A single "rate this answer 1 to 10" judge.
Learn it

Q16How do you defend against prompt injection?Ch. 18
They check
That you know a prompt cannot be the security boundary.
Answer
  1. The root cause: instructions and data arrive in the same channel, so text in a document or a message can act as an instruction.
  2. Layers, strongest first: least privilege for tools; a person confirms write actions; control what gets indexed; an output guard in code; an input guard.
  3. The first layers limit the damage even when an attack gets through; the guards catch what slipped past.
Follow-up
"What is indirect injection?" Instructions planted in content the system retrieves, such as a wiki page anyone can edit.
Avoid
"I tell the model to ignore malicious instructions."
Learn it

Q17How do you reduce hallucinations?Ch. 2, 4, 17, 18
They check
That you treat it as several fixable causes, not one mysterious flaw.
Answer
  1. Give the facts: retrieval or a tool, and check that the right chunk was retrieved.
  2. Give a way out in the prompt: "if the passages don't answer, say so", and "use only the passages".
  3. Check after: code verifies the cited source was among the passages; a judge checks every claim is supported.
  4. Measure it with cases the documents cannot answer, where the right output is "I don't know".
Follow-up
"Will a bigger model fix it?" Not when the fact was never in the prompt.
Avoid
"Set temperature to 0." It makes the guess repeatable, not true.

Q18What do you monitor in production, and how do you cut cost and latency?Ch. 19
They check
That you measure before you optimise, and know where the money goes.
Answer
  1. Log every model call: tokens in and out (thinking tokens are billed as output), duration and time to first token, model and exact version, prompt version, errors and retries, and a request ID that joins the steps into one trace.
  2. In this book, about 95% of the time was the model call; retrieval was about 50 ms. So speed up the model part: fewer calls, shorter outputs, streaming, a smaller model where evals allow.
  3. Three caches: exact (same question; clear it on re-index), semantic (similar question; can answer the wrong one), and the provider's prompt caching (a repeated prefix; no correctness risk).
Follow-up
"Is logging full prompts a problem?" They are user data: decide who can read them and for how long.
Avoid
Optimising retrieval before measuring where the time goes.
Learn it

Q19When would you finetune a model?Ch. 20
They check
That finetuning is the last thing to try, and you know form from facts.
Answer
  1. First ask: missing facts, or wrong behaviour? Missing or changing facts go to retrieval or a tool: an index updates in minutes.
  2. Wrong behaviour goes to a better prompt, examples and smaller steps, measured by evals.
  3. Finetune when a strict format or style will not hold, a narrow high-volume task could run on a much smaller model, or the prompt has grown huge with examples; with hundreds of good examples, a stable task and an eval.
  4. LoRA trains a small add-on instead of all the weights, which makes it much cheaper.
Follow-up
"What does it cost after training?" A better base model will come; your finetune does not move to it.
Avoid
"We'll finetune it on our documents so it knows them."
Learn it

Designing the system

Q20Walk me through how you would build a question-answering assistant over company documents.Ch. 21, 22, 24
They check
That you start small, measure, and add parts in order, not draw the finished diagram first.
Answer
  1. Start from the problem: who asks what, and should this be an AI feature at all; facts that live in systems stay in code. Do the budget sum: time and cost per question, at your volume.
  2. Ten cases first: real questions and the answers you would accept. Then one call, a prompt, a model and a score.
  3. Add the facts (retrieval, or a lookup) and score again; then fix the worst failure, one change at a time, keeping or undoing each.
  4. Add checks and a log of tokens, time and errors; then three real users, whose questions become new cases.
  5. Parts are added only when a failure asks for them: usually context first, then guardrails, then routing, caching and agent logic.
Follow-up
"What would you not build in version one?" An agent, a semantic cache, finetuning, a graph: each waits for a measured need.
Avoid
Opening with the tools ("I'd use LangChain and Pinecone") instead of the problem.

Q21What is evaluation-driven development?Ch. 17, 24
They check
That you know the term, and that you work this way, not only that you can define it.
Answer
  1. Decide how the application will be judged before you build it: the cases, what a good output looks like, and the other criteria such as cost and latency. The name, from Huyen's AI Engineering, comes from test-driven development.
  2. In practice: ten real inputs with the answers you would accept, and a score, before the first prompt; then every change is kept or undone by that score.
  3. It changes what you build: AI Engineering notes that the applications most common in production are the ones with clear evaluation criteria.
Follow-up
"What if the output is open-ended?" Code checks for what can be checked, a tested judge for meaning, and people on a sample.
Avoid
"We add evals once the product works." By then nobody can say whether it works.
